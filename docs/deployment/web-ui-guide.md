# Web UI User Guide

The Containerization Assist Web UI provides a browser-based interface for creating and monitoring containerization jobs. An AI agent autonomously analyzes your code, builds Docker images, and deploys to Kubernetes.

## Creating a Job

Navigate to **New Job** and choose how to provide your repository source code.

### Git URL (recommended)

Paste a GitHub, GitLab, or any HTTPS git URL. Public repositories work without authentication.

| Field | Required | Description |
|-------|----------|-------------|
| Repository URL | ✅ | `https://github.com/org/repo` |
| Branch / Tag | — | Defaults to the repo's default branch |
| GitHub Token | — | For private repos: a Personal Access Token (PAT) or GitHub App installation token |
| Container Registry | ✅ | Where to push built images (e.g., `myacr.azurecr.io`) |
| Target Namespace | ✅ | K8s namespace for deployment (e.g., `test-myapp`) |
| Image Name | — | Auto-derived from repo name if omitted |

**Example — public repo:**
```
Repository URL: https://github.com/Azure-Samples/todo-nodejs-mongo
Registry:       myacr.azurecr.io
Namespace:      test-todo
```

**Example — private repo:**
```
Repository URL: https://github.com/my-org/internal-service
GitHub Token:   ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Registry:       myacr.azurecr.io
Namespace:      test-internal
```

### Upload Archive

Upload a `.zip`, `.tar.gz`, or `.tgz` file containing your project source code.

### Local Path

For development/testing when the API server has filesystem access to the repo. Enter the absolute path on the server (e.g., `/home/user/my-project`).

## Monitoring a Job

After creating a job, you're taken to the **Job Detail** page showing:

### Pipeline Visualization

A horizontal stage diagram tracks progress through the 10 pipeline stages:

```
🔍 Analyze → 📝 Dockerfile → 🏗️ Build → 🔒 Scan → 🏷️ Tag → 📤 Push → ☸️ Manifests → 🖥️ Cluster → ✅ Verify
```

Each stage shows:
- ✅ Green — completed successfully
- ❌ Red — failed
- 🔵 Blue — currently running
- ⬜ Gray — not yet reached
- 🛡️ Badge — policy validated (on mutating stages)

### Validation Gates

After each **mutating stage** (Dockerfile generation, build, manifest generation), a validation gate shows whether the output passed policy checks:

- ✅ **Policy passed** — all checks satisfied
- ❌ **Policy failed** — click to expand and see specific violations
- ⚠️ **Warnings** — non-blocking issues to review

### Artifact Revisions

The **Artifacts** tab shows how generated files evolved through the pipeline:

1. **Dockerfile Plan** — generated by `generate-dockerfile`, shows base images and recommendations
2. **Dockerfile** — validated by `build-image-context`, shows final build configuration
3. **K8s Manifest Plan** — generated by `generate-k8s-manifests`, shows deployment configuration

Each revision includes the producing tool, step number, content preview, and policy validation result.

### Raw Steps

The **Raw Steps** tab provides full JSON input/output for every tool execution, useful for debugging.

## Policy Configuration

Navigate to **Policy** to configure validation rules.

### Allowed Base Images

Restrict which Docker base images the AI agent can use. For example:

```
mcr.microsoft.com/
node:22-alpine
python:3.12-slim
```

This auto-generates an OPA Rego policy that blocks any Dockerfile using a base image not in your list.

### Custom Rego Policies

Author your own OPA Rego policies directly in the **New Session → Policies → Custom Policy → Custom Rego** panel. Policies are evaluated against generated Dockerfiles and Kubernetes manifests during pipeline execution.

The editor provides Rego syntax highlighting, a **Validate** button that compiles the source through the policy sidecar, and inline error surfacing (line/column highlight) for parse failures. The **Add Policy** button is gated on successful validation.

**Violations must be objects with `rule` and `message` fields** (strings are ignored by the evaluator):

```rego
package custom.require_healthcheck

import rego.v1

violations contains v if {
  input.type == "dockerfile"
  not contains(input.content, "HEALTHCHECK")
  v := {
    "rule": "require-healthcheck",
    "message": "All Dockerfiles must include a HEALTHCHECK instruction",
  }
}
```

Custom Rego requires the **policy sidecar** service. It ships with the standard `docker compose up` deployment and is reachable by the API via `CA_POLICY_SERVICE_URL`. For local `./dev.sh` development, either run docker-compose alongside your dev server or install the `opa` binary on your PATH — custom Rego policies are silently skipped at runtime otherwise.

### Built-in Policies

The system includes built-in policies for:
- **Base image governance** — blocks deprecated versions, recommends Alpine/distroless
- **Security baseline** — requires non-root user, blocks secrets in build args
- **Container best practices** — layer optimization, multi-stage builds

## Authentication

### For Private Repositories

You can authenticate to clone private repos two ways:

1. **Personal Access Token (PAT)** — Generate at GitHub → Settings → Developer settings → Personal access tokens. The token needs `repo` scope. Enter it in the "GitHub Token" field when creating a job.

2. **GitHub App Installation Token** — If you've installed a GitHub App on your organization, use the installation token. The token is injected as `https://x-access-token:<token>@github.com/...` during clone.

### For the REST API

If `CA_API_KEY` is configured on the server, you'll need to set your API key in the browser. Open browser DevTools console and run:

```javascript
localStorage.setItem('ca-api-key', 'your-api-key-here');
```

Then refresh the page.
